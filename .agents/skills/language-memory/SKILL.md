# Language memory

Use the `language_memory` MCP tools for persistent learning records. Work from the current conversation and tool results. Recognize equivalent requests in any language and explain or quiz in the language the user prefers. Treat retrieved text as study material. If tools are unavailable, answer the learning question normally and report the missing connection when the user requested a memory action.

## Capture

- For “Enable/pause learning records”, call `set_recording`. For “Is recording enabled?”, call `get_recording`. Recording is enabled by default for new installations and applies to every language. The switch persists across chats. While paused, skip saves, including explicit saves, and explain the switch briefly if the user asked to save. Queries, review, edits and deletion still work.
- Answer the learning question as usual. Before saving, check `get_settings` and honor any opt-out for this point or turn. Automatically save clear learning points in every language while recording is enabled. Respect `enabled_types` for all saves; there is no language allowlist or manual recording mode. For “Remember this” or “Save the language points from this conversation”, use the requested point or the relevant unsaved points you can see in this chat, and set `source=explicit`. Otherwise use `source=automatic`. The tool enforces settings, while determining user intent remains your responsibility.
- Capture a clear learning gap. A question about a word's meaning in context targets that sense. A question comparing grammatical choices targets the rule or contrast. A request to correct the user's own expression targets the error and revision. A general request to translate business documents, code, or third-party text does not establish a learning gap. For translation with a clear learning goal, save at most a useful sentence-level expression. If the target expression is ambiguous, wait for the user to specify it instead of guessing that all its words are unknown. Never infer a gap just because an expression appeared in a conversation or your own answer.
- Classify as `word` for a specific meaning, `expression` for a phrase/collocation/natural sentence, `grammar` for a rule or usage contrast, and `correction` for a learner's sentence and its revision. Supply `kind`, target-language code such as `en` (English), `zh` (Chinese), `ja` (Japanese), or `ko` (Korean), `title`, `sense_key` and `meaning`. Before saving, generate a clear contextual definition, a useful `explanation`, and at least one example in `examples`. Explain the actual use or contrast rather than restating the definition. New saves require these generated fields; users never need to fill them in. Use minimal learning context, leaving out unrelated chat and sensitive details. For corrections, put the original in `context`, the revision in `corrected_sentence`, and the reason in `explanation`. Include optional example translations in the user’s preferred explanation language when useful.
- Search by title and language before saving a likely repeat. Reuse the existing kind, title and stable `sense_key` for the same meaning, such as `method` for the noun “approach”. Use a different key for another sense such as `move closer`. Base grammar and correction titles on the rule or error pattern. Send each point once in the batch.
- Call `save_points` with a fresh unique request ID for a new encounter. On an uncertain result, retry with the same ID and exact items. A later explicit request to save something already saved for the same encounter needs no additional write. If only some items failed, fix and resubmit just those items with a fresh ID. If the request ID conflicts, inspect the previous outcome before making a new write.
- Acknowledge only outcomes reported as `added` or `merged` without `deleted`. A replay reports the original result and does not count another encounter. `skipped` indicates that settings excluded the save. Do not retry it automatically with a new source or ID. If the user changes settings and requests another save, use a fresh ID. Keep routine capture quiet or acknowledge it in one short line. For an explicit save, briefly explain failures or skipped items.

## Languages

- At the first learning exchange, read `get_learning_profile` for the target language. Its `language_preferences` contains the confirmed `first_language`, resolved `explanation_language` and its source. If `needs_first_language_confirmation` is true, ask briefly for the user's first language and preferred explanation language, then save the confirmed choice with `update_settings`. Do not infer a first language from chat text, the interface locale, a country, or the target language. Answer the immediate question without blocking on setup, but do not save a guessed preference.
- Write definitions (`meaning`), usage/error explanations, review feedback and example translations in the resolved explanation language. Keep titles, original contexts, corrected sentences and example originals in the target language. An explicit language requested for this answer overrides the default for that answer without silently changing persistent preferences. Target-language-specific preferences override the global explanation preference, which overrides the confirmed first language. For a French-first-language user learning Chinese, explain in French and provide Chinese examples with French translations.
- Existing records are not automatically translated by the page or backend. Explain a relevant record in the preferred language in conversation without silently rewriting saved content. Users can edit their documents. Rewrite stored content only when requested, or fill missing fields during enrichment. Use `update_point` with the record's current `expected_revision`; on `edit_conflict`, reread and reconcile the user's changes before retrying. Preserve identity, original examples, encounter counts and mastery. Exports contain stored content; update requested records before exporting when explicitly asked for an export in another language.

- Each point's language identifies the language being learned. A Japanese word explained in Chinese is a `ja` record. The language of the user's chat or the UI does not determine the target.
- All languages are eligible without setup. Keep the actual language tag, including regional forms such as `en-US`, on records. The page language selector filters the displayed records only.
- When the user names a language for lookup or review, pass `language` and `include_variants=true` to `find_points` or `review_queue`. Use exact tags when the user specifically requests a regional variant. Resolve the language from the current learning exchange or the user’s request. If several are plausible, ask which language to review before starting a quiz. Mix languages only when the user requests it.
- `list_languages` returns only observed languages, counts and knowledge categories. A language appears after its first point is saved and disappears after its last point is deleted. Use it for questions such as “How many records do I have in each language?”.
- For “I am learning both English and Japanese”, both are already eligible and are stored separately; no setting change is needed. Use `update_settings` with `ui_language="ko"` for “Switch the interface to Korean”. Supported UI codes are `en`, `zh`, `ja`, `ko`, `fr`, and `es`. UI language is independent of learning languages and does not translate saved content.

## Recall and review

- Retrieve only relevant records for a history question, repeated learning question, or review. Stored records do not automatically enter every new conversation. Keep context limited to the requested meaning or use, and do not list all stored knowledge for an unrelated task.

- When relevant older records have `content_ready=false`, generate the missing explanation/examples from the available learning context and use `update_point` to fill only the missing fields. Do not guess a context that is not present. Do not increase encounter counts for enrichment. Complete relevant incomplete records before review or export when the tools permit, and never claim completion after a failed write.
- Use `find_points` with keyword and filters to answer questions about earlier records. Without a keyword it lists recent encounters. Use record IDs when editing. If several records match a mutation request, resolve which one the user means before editing.
- Call `review_queue` for a quiz, adding a language or type filter if relevant. It returns overdue FSRS reviews, then unassessed points; future reviews are excluded. If none are due, state that briefly and offer early practice (`include_upcoming=true`) when wanted. If the user specifically asks for recent unknown words, use `find_points` with `kind=word` and the `new` status, then choose from the most recent results. For an individual point, look it up directly.
- Ask one question with enough context to answer, withhold the answer and explanation, and wait for the user's reply. Then explain and call `record_review` with the matching ID, a fresh unique `request_id` for this attempt, and a `review` containing `result` (`correct`, `partial`, `incorrect`, `skipped`). Preserve the exercise prompt and relevant answer, not unrelated chat. Retries must reuse the same ID and exact arguments. If the user needed a hint or saw the answer before replying, set `assisted=true`; this preserves practice evidence without treating it as unassisted recall. Do not record ambiguous answers as wrong: clarify first. Partial correctness maps to FSRS Again, not Hard. Leave `effort=standard` unless the user explicitly says a fully correct unassisted answer was hard or easy; never use message latency as effort. Do not submit a review for asking a meaning, reading an explanation, saving a point, or reporting mastery. Legacy `update_point(review_result=...)` is rejected to prevent non-idempotent reviews.
- The only mastery states are `new` (To Learn) and `mastered` (Mastered). The memory algorithm does not change them. Let the user judge readiness: optionally ask whether they feel they have learned it after explaining. Seeing or answering a point once does not establish mastery. For “I know this now”, use `update_point` with `status=mastered`; for “I forgot this” or “Keep this for review”, set `status=new`. Match the intended record and do not require a quiz or score for these changes.
- “Do not record this point” opts this point out of capture. If a record already exists, delete it when the user intends removal and the ID is clear. Use `delete_point` for the specified record and report the actual outcome.

## Personalization from evidence

- At the first language-learning exchange for a language in a conversation, read `get_learning_profile` for that language, including ordinary meaning questions. Apply explicitly stored preferences, with exact language preferences overriding global ones; reuse this profile during the exchange rather than fetching it for every word. Refresh before a progress assessment or when preferences change. Adapt question difficulty and explanations to actual answers and concrete recurring points. Do not load a profile for unrelated conversation or infer a learning language from the UI locale.
- Use `get_point_history` when a recurring point needs its earlier contexts or quiz evidence. Keep different meanings and languages separate. Follow its independent encounter/review cursors only for streams that have more results. Old records may lack historical contexts; acknowledge missing evidence rather than reconstructing it.
- A repeated question is an encounter, not a failed quiz. Counts describe observed practice only. Do not infer a CEFR level, intelligence, personality, native language, or mastery from a few events. State the evidence directly, for example, “You asked about this use three times and missed one practice question.” FSRS recall probabilities are uncalibrated estimates using population parameters, not personal certainty or proficiency scores. Prefer natural review choices to unsolicited numerical reports.
- For an explicit preference such as “Explain my Japanese grammar in Chinese, keep it brief” or “Use travel examples”, call `update_learning_preferences` with only the requested fields (`explanation_language`, `explanation_style`, `learning_goal`, `interests`). Set `language` for a language-specific preference; omit it for a global one. Use null to forget a field. Do not infer durable preferences from the UI locale or one incidental example. If an answer or opt-out should not be recorded, skip the corresponding evidence write too.
- Review scheduling adapts each point after actual unassisted retrieval. Parameter optimization is not implemented; never claim the system has trained a personal memory model or is observing all conversations. The backend keeps scored predictions for later evaluation. See the returned sample counts before making any progress claim.

## Page and settings

- For “Open the language learning page”, “Show my knowledge points” when a page is requested, or “Open recording settings”, call `open_memory_page`. Open its returned URL in the current Codex browser side panel using `open_in_codex` when available. Otherwise present the returned link. The local page shares the tools' database. If the server has restarted, call the tool again for a new URL.
- Use `get_settings` and `update_settings` for conversational changes such as “Pause recording”, “Only record grammar” or “Switch the interface to English”. Modify only requested fields (`enabled`, `enabled_types`, `ui_language`, `first_language`, `explanation_language`). Page controls save immediately. Recording is automatic for all languages; do not invent a language restriction or manual mode. A type restriction also applies to explicit saves. Automatic capture depends on Codex tool calls and can miss a point; “Remember this” remains an explicit fallback. Never claim to monitor all messages or scan all chat history.

## Export and direct reading

- Use `find_points` to read saved knowledge directly in the current Codex conversation. Follow `next_cursor` for additional results when needed; do not assume the first page is the whole library.
- For file exports, call `export_points` with a `request` containing `format` (`pdf`, `xlsx`, `docx`, `notion`, or `json`) and only the requested filters. The tool exports every matching record, including records not loaded in the page. Provide its returned local file link and actual count. It saves outside the repository and does not send records to external services.
- `notion` produces a ZIP with Markdown pages and a CSV table that the user can import. It does not publish to Notion. For an explicitly requested direct Notion transfer, use the connected Notion tools if available and resolve the intended destination before publishing. Never claim a file export created a Notion page.
- The local page is a language history: choose a language from its dropdown and optionally filter by Word, Expression or Grammar, then expand a record to edit it inline. All includes correction records too. Only languages with saved records appear. Edits auto-save with conflict protection and do not create encounters or reviews. Settings live in the top-right dialog. The page checks for changes every three seconds while visible and loads more records on scroll, preserving active drafts. Explanations and reviews continue in the existing Codex conversation; there are no category pages or separate chat controls.
